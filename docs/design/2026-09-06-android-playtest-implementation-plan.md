# Android Playtest 两日实施计划

日期：2026-09-06。目标：用户所述两天后的 Android 手机／平板试玩。
状态：实施顺序建议；规则依据为已同步的 revision 9 和本轮用户确认的新增需求。本文不替代 Claude 的正式设计文档，不表示新增规则已经实现。

## 目标与工作方式

交付一个可连续试玩的版本：鱼有基础行为与动画，生成不被石头遮住；提竿判定更宽容；远距离捕获、擦边和加速有清楚的得分回报；Android 操作、结束和重开形成完整流程。

继续教学模式。每个步骤先简述思路、修改入口和观察结果，再由用户操作；不一次倾倒整个阶段的实现。文件与接线可由 Codex 主动读取，不反复要求截图。只有用户另行要求代写，才直接修改该部分代码／场景。

用户已延后全面回归测试，以试玩体验推进。每个新增功能只做与其直接相关的最小观察，最后在目标设备打开、完成一局并重开；未检查的路径不记作通过。

## 明确的规则合同

### 提竿与冷却

- 提竿在 Striking 中进行，正式枚举名称为 Striking，不是 Strike。
- 保留 Striking 中判定失败后的 attemptCooldown：期间忽略新尝试，不刷新冷却；圈继续运动。
- 新增 ReadyToCast 中的 postAttemptCooldown：从 Striking 超时，或 Reeling 成功收鱼/空钩/撞石/断线返回时启动。冷却中可移动，不能抛竿；抛竿语义输入及手势检测均应关闭，避免缓存手势稍后触发。
- 初次开局不自动加这段冷却；直接进入 GameOver 时不进入可操作的 ReadyToCast。
- Striking 成功后仍立即进入 Reeling，不增加成功后等待。用户最后一句“从 Strike 和 ReadyToCast”按上下文解释为从 Striking/Reeling 返回 ReadyToCast 都冷却；这项解释在给 Claude 的交接中明确保留，实施前口头确认状态路径即可。
- 两种冷却分开调参。首版建议共用一个 postAttemptCooldown 值处理各返回原因，不为每条路径增加独立参数。
- 时机圈执行 revision 9：每次随机目标带中心、固定带宽；隐藏容错；外→内→外共两程，首次成功结束。沿用其参数建议，不加入 Perfect/Good 或提竿精度加分。

### 得分

最终得分 = 鱼种基础分 × 纵向回收距离倍率 + 擦边奖励累计 + 加速回收奖励累计。

- 距离取成功咬钩点到岸边的纵向距离，作为该次捕获的固定记录；不累计左右移动，也不分别叠加一套“抛竿距离分”。
- 带鱼 Reeling 时才累计技巧分。加速分按按住加速期间实际向岸边移动的距离计算，不按按住时间计分。
- 擦边是靠近障碍而不碰撞，并成功通过它到靠岸一侧；接近即加分不成立。每块障碍每次收线最多一次。
- 擦边与加速可叠加。技巧分先属于本次待结算值，成功上岸后一起计入 ScoreTracker；撞石、断线等未上岸结果不结算该鱼。整局时间耗尽时的在途奖励按未捕获处理是建议边界，需写入正式规则。
- UI 读取同一份结算数据：途中显示暂存奖励，成功后展示基础分、距离倍率、两类技巧分和合计。动画只演示，不逐段重复调用 AddScore。
- 系数、倍率曲线/范围、整数取整方式尚未最终选定；进入计分步骤前由用户选择一版，写入 Profile，不把示例 +20 等数值当成已定平衡值。

### 鱼行为和生成

- 最小行为树优先级：已挂钩→跟随；正在参与咬钩竞赛→接近鱼饵；否则→停留/选择游动点/游动。
- Animator 表现对应 Idle / Swim / Hooked；行为树负责决策，动画不决定谁咬钩。FishBiteRaceController 仍是唯一获胜者裁决方。
- 两天内不建设通用行为树框架/编辑器，不引入未经选择的新插件；优先最小可扩展节点结构。
- 生成点需避开石头可见遮挡区域并考虑鱼的体积与边距。不是禁用石头整条靠岸方向，也不是检测未来回收路线。
- 优先用作者可编辑的生成排除轮廓覆盖石头可见区域；与玩法碰撞体分离，避免为生成而改变碰撞难度。若用 SpriteRenderer.bounds，注明其保守矩形与透明边缘导致的额外排除。
- 保留鱼间间距和有上限的随机重试；区域拥挤时少生成，不能为了凑数生成到石头下面。
- 防止生成后立即游进石头图像下是关联的巡游建议，区别于用户已确认的“初始生成避遮挡”；若试玩出现再决定是否扩展路径检查，不直接引入寻路。

## 数据与组件分工（新增名称为建议）

| Profile / 数据 | 参数范围 | 运行时所有者 |
|---|---|---|
| StrikeWindowProfile | 两程时长、带宽、随机中心范围、隐藏容错、尝试冷却、拒绝反馈参数 | StrikeController；HUD 只读取本次实际带位置 |
| FishingLoopProfile（新增） | 返回抛竿冷却、初始鱼钩数、整局时间 | FishingLoopController / HookTracker / SessionTimer |
| ReelTuningProfile | 回收/加速/横移速度和现有张力值 | ReelingController |
| FishDefinition（新增） | 鱼种名称、基础分、对应行为 Profile；美术关联按现有 Prefab 组织 | 单条鱼与生成器 |
| FishBehaviorProfile（新增） | 停留时间范围、游动速度/范围、接近速度等行为调参 | 鱼行为执行组件 |
| ScoreTuningProfile（新增） | 距离→倍率、加速每单位距离奖励、每次擦边分数、擦边距离阈值 | 本次收线计分组件，成功后提交总分 |
| FishSpawnProfile（新增） | 数量、间距、遮挡安全边距、最大重试次数 | FishSpawner |
| FishingFeedbackProfile（按需新增） | 提示/分项动画时长、弹出位移、缩放等需反复调整的表现参数 | UI / 反馈组件 |

所有手感、平衡和需要反复调整的数值进入相应 Profile；不要把每帧张力、已奖励障碍集合、实际随机带位置、当前得分等运行状态写入共享 Profile。场景对象、UI 引用、泳区/排除区位置仍留在场景。新 Profile 用清楚的 Header、Tooltip、范围及关联约束；不用重置用户现有调参来“对齐示例”。

## 两天实施顺序

| 阶段 | 最小交付 | 依赖/观察点 |
|---|---|---|
| 第一天 A：场景与 Android 操作 | 确认唯一交付场景，补加速按钮按下/松开，沿用校准流程 | 设备上可开始收线并主动加速；已有接线就跳过 |
| 第一天 B：revision 9 + 冷却 | Profile 扩展、随机带、往返圈、容错、两个来源返回冷却 | 看得到第二次机会；收线和提竿超时后可移动但暂不能抛 |
| 第一天 C：得分核心 | 鱼种数据、固定距离记录、加速距离奖励、障碍擦边一次性奖励、上岸统一结算 | 一次捕获能解释分数来源；先有文字分项，再做动画 |
| 第二天 A：生成与鱼 AI | 避遮挡、基础行为树、Idle/Swim/Hooked 动画连接 | 出生可见，鱼会活动、接近鱼饵、被钩住 |
| 第二天 B：反馈与闭环 | 得分动效、成功/失败原因、核心音效、简短移动端提示、结果重开 | 玩家不依赖开发者解说也知道发生了什么 |
| 第二天最后约 1/4：交付 | Android 包、目标设备完整一局和重开、备份可运行版本 | 只处理明显阻断与展示问题，不开启新系统 |

每个半天保留一份可继续玩的状态；不同时拆开计分、AI、UI 后等最后才整合。教学速度和素材准备会影响排期，本表是顺序和取舍，不是两天完成所有细节的保证。

## 工作量超过两天时怎么取舍

先压缩实现深度，不静默删除用户已选功能：计分只用一种擦边奖/一种加速奖；鱼种复用可用素材；行为树只做三个主分支；UI 分项使用一种通用动画，不另造完整结算场景。

优先保留 Android 操作、计分可解释性、生成不遮挡、基础鱼活动、revision 9、冷却及重开。若这些最小版本仍超时，列出剩余内容由用户选择，不把未完成项标成完成。

候补且不占主任务时间：正式抛竿弧线与更复杂动画衔接、丰富声音层次、精细得分特效、完整暂停菜单/暂停内重校准。继续延期：诱饵摆动、个人力度校准、随机障碍关卡、复杂鱼群协同/寻路、更多计分种类、文件夹整理和插件安装、WebGL 发布及系统回归。
